# Accounting-of-events

Консольная система учёта и организации университетских мероприятий. Программа позволяет регистрировать пользователей, выполнять вход в систему, просматривать мероприятия, создавать мероприятия от имени организатора и записывать студентов на доступные мероприятия.

**Цель системы:** оптимизировать процессы учёта и организации мероприятий в университете.

## Что отслеживается

- **Мероприятие:** название, описание, дата и время, место, организатор, максимальное количество участников и тип мероприятия.
- **Статус мероприятия:** запланировано (`planned`), завершено (`completed`) или отменено (`cancelled`).
- **Записи студентов** на мероприятия.
- **Статус записи:** активна (`registered`) или отменена (`cancelled`).
- **Посещаемость:** поле для хранения отметки о посещении (`attended` / `absent`).
- **Пользователи** системы и их роли.

## Пользователи и их права

### Организатор

В текущей консольной версии организатор может:

- просматривать список мероприятий;
- создавать мероприятия;
- завершать мероприятия;
- отменять мероприятия.

В сервисном слое также предусмотрены операции изменения и удаления мероприятия, однако отдельные пункты для этих операций пока не добавлены в пользовательское меню.

### Студент

В текущей консольной версии студент может:

- просматривать список мероприятий;
- записываться на мероприятие по его ID;
- просматривать собственные регистрации и их статусы.

### Регистрация пользователя

При регистрации пользователь вводит ФИО, логин, пароль и самостоятельно выбирает роль: студент или организатор. Отдельной роли администратора и механизма подтверждения роли организатора в текущей реализации нет.

## Основные функции системы

- **Регистрация:** создание учётной записи с указанием ФИО, уникального логина, пароля и роли.
- **Авторизация:** проверка логина и пароля, получение данных пользователя и открытие меню в соответствии с его ролью.
- **Управление мероприятиями:** создание мероприятия, изменение его статуса на завершённое или отменённое.
- **Запись на мероприятие:** проверка существования пользователя, его роли, существования мероприятия, статуса мероприятия и наличия свободных мест.
- **Просмотр регистраций:** студент может увидеть свои записи, статус каждой записи и состояние посещаемости, если оно заполнено.
- **Экспорт данных:** при запуске программы данные о мероприятиях и связанных с ними организаторах и типах мероприятий экспортируются в JSON, XML, YAML и CSV.

## Технологии

- **C++17** — язык программирования.
- **CMake** — система конфигурации и сборки проекта.
- **SQLite** — встроенная реляционная база данных.
- **SQLite3 C API** — взаимодействие приложения с базой данных.
- **OpenSSL** — генерация соли и хеширование паролей с помощью PBKDF2-HMAC-SHA256.
- **JSON, XML, YAML, CSV** — форматы экспорта данных.

### 1. Пользовательский интерфейс — UI

Слой UI отвечает за взаимодействие с пользователем:

- вывод главного меню;
- регистрацию и вход;
- отображение меню студента и организатора;
- получение данных, введённых пользователем;
- вызов соответствующих сервисов;
- вывод результатов операций и сообщений об ошибках.

Интерфейс не должен самостоятельно выполнять SQL-запросы и реализовывать бизнес-правила. Для этого он обращается к сервисному слою.

### 2. Сервисный слой — Services

Сервисы содержат бизнес-логику приложения.

- **AuthenticationService** — регистрация пользователей, проверка логина и пароля, хеширование паролей. Для хеширования используется PBKDF2-HMAC-SHA256 с солью.
- **EventService** — проверка данных мероприятия, проверка организатора и типа мероприятия, создание мероприятия, изменение его данных и управление статусом.
- **RegistrationService** — запись студента на мероприятие и отмена регистрации. Перед созданием записи проверяются роль пользователя, статус мероприятия и количество свободных мест. Операция записи выполняется с использованием `SAVEPOINT`, чтобы при ошибке отменить частичные изменения.

Сервис обращается к репозиториям для получения и сохранения данных. Таким образом, правила работы системы находятся отдельно от интерфейса и SQL-запросов.

### 3. Слой репозиториев — Repositories

Репозитории отвечают за непосредственные операции с таблицами базы данных. Они выполняют SQL-запросы и преобразуют полученные строки в объекты моделей C++.

- **UserRepository** — создание пользователей, поиск пользователя по ID и логину.
- **EventRepository** — создание, получение, изменение и удаление мероприятий.
- **EventTypeRepository** — получение и работа с типами мероприятий.
- **RegistrationRepository** — создание, получение и изменение записей студентов на мероприятия.

### 4. Слой базы данных — Database

Этот слой обеспечивает соединение с SQLite и выполнение SQL-команд.

- **Database** открывает файл базы данных, настраивает соединение, включает проверку внешних ключей и закрывает соединение при завершении работы.
- **Statement** — вспомогательный класс для подготовки SQL-запросов, привязки параметров, выполнения запросов и чтения результатов. Деструктор освобождает подготовленный SQLite statement.

Для SQL-запросов с параметрами используются подготовленные выражения SQLite. Это позволяет не подставлять пользовательские значения непосредственно в текст SQL-запроса.

### 5. Модели — Models

Модели описывают основные сущности предметной области в виде структур C++.

- **User** — пользователь: ID, ФИО, логин, хеш пароля и роль.
- **Event** — мероприятие: ID, название, описание, место, дата и время, максимальное количество участников, статус, ID организатора и ID типа.
- **EventType** — тип мероприятия: ID и название.
- **Registration** — запись студента: ID записи, ID мероприятия, ID студента, статус регистрации и необязательный статус посещаемости.

В моделях также определены перечисления для ролей пользователей и статусов мероприятий, регистраций и посещаемости.

### 6. Модуль экспорта — Exporters

`DataExporter` отвечает за выгрузку информации из SQLite во внешние форматы.

Последовательность работы:

1. Выполняется SQL-запрос к базе данных.
2. Результат преобразуется во внутреннюю универсальную структуру `Value`.
3. Данные сериализуются в JSON, XML, YAML и CSV.
4. Создаётся каталог `out`, если его ещё нет.
5. В каталог записываются файлы экспорта.

Для формирования вложенных объектов в SQL-запросе используются псевдонимы столбцов с разделителем `__`. Например, `organizer__name` преобразуется во вложенный объект `organizer` с полем `name`.

### 7. Точка входа — main.cpp

`main.cpp` связывает все компоненты приложения:

1. Открывает базу данных `accounting.db`.
2. Создаёт объект `DataExporter` и выполняет экспорт мероприятий.
3. Создаёт репозитории.
4. Создаёт сервисы и передаёт им необходимые репозитории.
5. Создаёт пользовательский интерфейс `ConsoleUI`.
6. Запускает главный цикл программы.

Если во время запуска возникает критическая ошибка, она перехватывается в `main.cpp` и выводится в консоль.

## Архитектура базы данных

Для хранения информации используется SQLite. База данных состоит из четырёх основных таблиц: `User`, `Event_type`, `Event` и `Registration`.

### 1. Таблица User — пользователи

Хранит учётные записи пользователей.

| Поле | Тип | Назначение |
|---|---|---|
| `ID` | INTEGER | Первичный ключ (PK) |
| `Full_name` | TEXT | ФИО пользователя |
| `Login` | TEXT | Логин пользователя, уникальный |
| `Password_hash` | TEXT | Хеш пароля с солью |
| `Role` | TEXT | Роль: `Student` или `Organizer` |

`ID` однозначно определяет пользователя. `Login` имеет ограничение `UNIQUE`, поэтому два пользователя не могут зарегистрироваться с одинаковым логином.

### 2. Таблица Event_type — типы мероприятий

Содержит справочник типов мероприятий.

| Поле | Тип | Назначение |
|---|---|---|
| `ID` | INTEGER | Первичный ключ (PK) |
| `Name` | TEXT | Название типа, уникальное |

Один тип мероприятия может использоваться у нескольких мероприятий.

### 3. Таблица Event — мероприятия

Хранит информацию о мероприятиях.

| Поле | Тип | Назначение |
|---|---|---|
| `ID` | INTEGER | Первичный ключ (PK) |
| `Title` | TEXT | Название |
| `Description` | TEXT | Описание |
| `Location` | TEXT | Место проведения |
| `Event_datetime` | TEXT | Дата и время |
| `Max_partipants` | INTEGER | Максимальное число участников |
| `Status` | TEXT | Статус мероприятия |
| `Organizer_ID` | INTEGER | Внешний ключ на `User.ID` |
| `Event_type_ID` | INTEGER | Внешний ключ на `Event_type.ID` |

`Organizer_ID` связывает мероприятие с пользователем-организатором. `Event_type_ID` указывает на тип мероприятия.

Для максимального количества участников установлено ограничение: значение должно быть больше нуля. Для статуса разрешены значения `planned`, `completed` и `cancelled`.

**Примечание:** в текущем SQL-файле базы данных название столбца записано как `Max_partipants` (с опечаткой). Это же написание используется в коде экспорта. При исправлении названия необходимо одновременно изменить схему БД и все обращения к этому полю в C++ и SQL.

### 4. Таблица Registration — записи на мероприятия

Связывает студентов с мероприятиями и хранит состояние их регистрации.

| Поле | Тип | Назначение |
|---|---|---|
| `ID` | INTEGER | Первичный ключ (PK) |
| `Event_ID` | INTEGER | Внешний ключ на `Event.ID` |
| `Student_ID` | INTEGER | Внешний ключ на `User.ID` |
| `Registration_status` | TEXT | `registered` или `cancelled` |
| `Attendance_status` | TEXT | `attended`, `absent` или `NULL` |

Ограничение `UNIQUE(Student_ID, Event_ID)` не позволяет создать несколько строк регистрации для одной пары «студент — мероприятие». Если студент отменил регистрацию, запись сохраняется в базе с соответствующим статусом.

`Attendance_status` может быть `NULL`, если посещаемость ещё не отмечена.

### Связи между таблицами

- **User — Event:** один пользователь-организатор может создать несколько мероприятий. Каждое мероприятие связано с одним организатором. Связь «один ко многим».
- **Event_type — Event:** один тип может относиться к нескольким мероприятиям. Каждое мероприятие имеет один тип. Связь «один ко многим».
- **User — Registration:** один пользователь может иметь несколько записей на мероприятия. Каждая запись относится к одному пользователю. Связь «один ко многим».
- **Event — Registration:** одно мероприятие может иметь несколько записей участников. Каждая запись относится к одному мероприятию. Связь «один ко многим».

Таким образом, таблица `Registration` реализует связь «многие ко многим» между пользователями-студентами и мероприятиями.

Внешние ключи включены при открытии соединения с SQLite с помощью `PRAGMA foreign_keys = ON`.

## Как начать использовать программу

### 1. Установка необходимых инструментов

Для сборки проекта необходимы:

- компилятор C++ с поддержкой C++17;
- CMake версии 3.16 или новее;
- библиотека SQLite3;
- библиотека OpenSSL.

#### Windows

Для Windows рекомендуется использовать **MSYS2 UCRT64**.

1. Скачайте установщик с официального сайта: https://www.msys2.org/
2. Установите MSYS2, используя стандартные настройки.
3. Откройте терминал **MSYS2 UCRT64** из меню «Пуск».
4. Обновите пакеты:

```bash
pacman -Syu
```

Если терминал попросит закрыть его после обновления, закройте окно, снова откройте **MSYS2 UCRT64** и выполните:

```bash
pacman -Su
```

5. Установите компилятор, CMake, Ninja, SQLite3 и OpenSSL:

```bash
pacman -S --needed mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja mingw-w64-ucrt-x86_64-sqlite3 mingw-w64-ucrt-x86_64-openssl
```

Для дальнейшей работы с проектом используйте именно терминал **MSYS2 UCRT64**.

#### Linux

Установите необходимые пакеты в соответствии со своим дистрибутивом.

**Fedora:**

```bash
sudo dnf install gcc-c++ cmake ninja-build sqlite-devel openssl-devel
```

**Ubuntu / Debian:**

```bash
sudo apt update
sudo apt install g++ cmake ninja-build libsqlite3-dev libssl-dev
```

После установки можно использовать обычный терминал Linux.

#### Проверка установки

Убедитесь, что компилятор и CMake доступны:

```bash
g++ --version
cmake --version
```

Если команды выводят версии программ, основные инструменты установлены.

cd accounting-of-events

### 6. Первое использование

При первом запуске программы система проверяет наличие учётной записи администратора.

Если администратор ещё не создан, автоматически запускается первоначальная настройка:
1. Введите ФИО администратора.
2. Укажите логин.
3. Введите пароль.
4. После успешного создания учётной записи программа перейдёт к главному меню.
При последующих запусках повторно создавать администратора не требуется.

Главное меню:
============================
     ACCOUNTING OF EVENTS
============================
1. Регистрация
2. Вход
0. Выход


Для начала работы обычному пользователю необходимо зарегистрироваться:
1. Выберите пункт 1. Регистрация.
2. Введите ФИО.
3. Укажите уникальный логин.
4. Введите пароль.
5. Выберите роль:
   - 1 — студент;
   - 2 — организатор.
6. После успешной регистрации вернитесь в главное меню и выполните вход.
Обычная регистрация не позволяет самостоятельно создать учётную запись администратора.

### 7. Работа в роли студента
После входа под учётной записью студента отображается меню:
1. Посмотреть мероприятия
2. Записаться на мероприятие
3. Мои регистрации
0. Выйти из аккаунта


Для просмотра мероприятий выберите пункт 1. Посмотреть мероприятия. Программа выведет список мероприятий с их идентификаторами и основной информацией.

Чтобы записаться на мероприятие:
1. Выберите пункт просмотра мероприятий.
2. Найдите ID нужного мероприятия.
3. Вернитесь в меню и выберите пункт 2. Записаться на мероприятие.
4. Введите ID мероприятия.
5. При успешной проверке система создаст регистрацию.
Система не позволит записаться на несуществующее, завершённое или отменённое мероприятие, а также при отсутствии свободных мест. Повторная регистрация на одно мероприятие также запрещена.

Пункт 3. Мои регистрации позволяет просмотреть мероприятия, на которые записан текущий пользователь.
8. Работа в роли организатора
После входа под учётной записью организатора отображается меню:
1. Посмотреть мероприятия
2. Создать мероприятие
3. Завершить мероприятие
4. Отменить мероприятие
0. Выйти из аккаунта


Для создания мероприятия выберите пункт 2. Создать мероприятие и укажите:
- название;
- описание;
- место проведения;
- дату и время в формате ГГГГ-ММ-ДД ЧЧ:ММ;
- максимальное количество участников;
- ID типа мероприятия.
Для создания мероприятия выбранный тип должен существовать в таблице Event_type. После успешного создания программа выведет ID нового мероприятия.

Для завершения или отмены мероприятия выберите соответствующий пункт меню и введите ID мероприятия. Завершённые и отменённые мероприятия недоступны для новых регистраций.

### 9. Работа в роли администратора
После входа под учётной записью администратора отображается меню:
1. Просмотреть пользователей
2. Изменить роль пользователя
3. Удалить пользователя
0. Выйти из аккаунта


Для просмотра зарегистрированных пользователей выберите пункт 1. Просмотреть пользователей. Программа выведет список пользователей с их ID, ФИО, логинами и ролями.

Для изменения роли выберите пункт 2. Изменить роль пользователя, укажите ID пользователя и выберите новую роль.

Для удаления учётной записи выберите пункт 3. Удалить пользователя. Программа автоматически выведет список пользователей. Укажите ID пользователя и подтвердите удаление.

Предусмотрены следующие ограничения:
- администратор не может удалить собственную учётную запись;
- нельзя удалить последнего администратора;
- регистрации удаляемого студента удаляются вместе с его учётной записью;
- удаление пользователя, на которого ссылаются другие записи, не выполняется.
После удаления программа обновляет список пользователей.

## Экспорт данных

Модуль `DataExporter` запускается автоматически при старте приложения. Он получает список мероприятий вместе со связанными данными организатора и типа мероприятия.

Результаты сохраняются в каталог `out` в корне проекта:

| Файл | Формат |
|---|---|
| `data.json` | JSON |
| `data.xml` | XML |
| `data.yaml` | YAML |
| `data.csv` | CSV |

Каталог `out` создаётся автоматически, если его ещё нет. Существующие файлы с такими именами перезаписываются при следующем запуске.

Экспорт выполняется при запуске программы. Изменения, внесённые пользователем уже после экспорта в текущем сеансе, попадут в файлы при следующем запуске приложения.
